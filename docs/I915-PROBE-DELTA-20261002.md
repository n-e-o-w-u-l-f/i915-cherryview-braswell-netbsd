## Implemented and verified within this audit: patch 0007

`patches/0007-i915-early-probe-resource-unwind-netbsd11.patch` changes
the failure after `i915_workqueues_init` from a direct return to
`goto err_early`. The workqueue initializer already frees its own partial
workqueue allocations on failure; jumping **after**
`i915_workqueues_cleanup` avoids a double cleanup. All early-probe
failure paths after sideband QoS registration now also call
`pm_qos_remove_request(&dev_priv->sb_qos)` before destroying locks and
uncore state. This matches the existing late-release ownership order.

- `tools/generate_early_probe_unwind_patch.py` checks the exact frozen NetBSD
  commit, unchanged input bytes and unique source anchors.
- `tests/test_early_probe_unwind.py` compiles the **actual transformed
  `i915_driver_early_probe` body** under strict host C11 warnings/errors.

  power-domain initialization and successful initialization.
- `git apply --check` succeeds against both the clean frozen NetBSD tree and

- Tests establish isolated cleanup control-flow semantics and patch

## 2026-10-02 continuation: OpRegion ownership and registration failure

The frozen NetBSD `intel_opregion_setup()` (display/intel_opregion.c:928+)
initializes `opregion->asle` only if firmware advertises `MBOX_ASLE`.
Its RVDA mapping is attempted inside a condition that requires non-NULL
`opregion->asle` and a nonzero ASLE RVDA/size. The frozen NetBSD
`intel_opregion_unregister()` unconditionally read
`opregion->asle->rvds`, even without an RVDA mapping. This is a
source-confirmed null-dereference risk for a supported OpRegion mailbox
configuration, regardless of whether it explains the HP black screen.

- `candidates/0009-netbsd-opregion-optional-asle-cleanup.patch` changes only
  that read to `opregion->rvda ? opregion->asle->rvds : 0`.
- In an independent **local, host-only** isolated C11 harness reproducing the
  exact frozen unregister function with candidate 0009's single substitution,
  four cases passed: no mapped header; header but no ASLE with notifier and
  firmware; ASLE but no RVDA; ASLE and RVDA. Compiler flags were
  `-std=c11 -Wall -Wextra -Werror -pedantic -fsanitize=address,undefined
  -fno-omit-frame-pointer`; output `OPREGION_UNREGISTER_HOST_C_OK`.
  This is **not** a native NetBSD object build or a live HP result.
- `tests/test_opregion_optional_asle.py` (commit 6e42f33) is a reproducible
  regression: it extracts the *actual* function from the pinned NetBSD
  checkout, checks the one-line candidate, compiles it with the same
  sanitizer tests, and runs `git apply --check` on that checkout. The new
  repository script itself has not been run on Legion because the recent
  command/synchronization route was externally blocked.
- Frozen `intel_irq_uninstall()` explicitly checks `drm.irq_enabled`
  before interrupt resource cleanup. The repeated IRQ-uninstall invocation
  in the old modeset/remove stack is guarded, not in itself proof of a
  double-free; the rest of teardown still requires semantic review.

`i915_driver_hw_probe()` calls `intel_opregion_setup()` **before**
`i915_driver_register()`. On failed `drm_dev_register()`, the
registration routine has not called `intel_opregion_register()`, but the
mapping created during HW probe may exist; the old failure path did not
unmap it. The 0008 candidate generator now calls
`intel_opregion_unregister(dev_priv)` on its explicit registration-error
unwind *before* the modeset/BIOS and power teardown. This makes candidate
0009 a mandatory predecessor to 0008, because an OpRegion without an ASLE
mailbox must also be safe on this error path.

The updated `tests/test_register_failure.py` checks this ordering and
requires composition of 0007, 0009 and the generated 0008 in a disposable
working directory. **The source-extracting Python tests and generator have
not yet run** on the pinned Git worktree because the Legion execution route
was externally blocked. Candidate 0008 is now published separately, but
Python-generator byte identity and native object compilation are unverified.
Verify the NetBSD `drm_dev_register()`/`drm_dev_unregister()` failed-registration
semantics and vGPU `display_ready` ordering before native integration.
None of COV-I915-005, COV-I915-011 or COV-I915-015 is closed.

### Candidate 0008 ordering correction and source composition

Source review against frozen NetBSD `i915_driver_remove()` and
`i915_driver_release()` found an **unsafe ordering in the first generator
revision**: it released GEM before the older integrated modeset and GVT
subsystems were removed. Generator commit `55cfadde` and test commit

OpRegion mapping first, quiesce GEM and atomic modeset, remove GVT and
modeset, then GEM and power domains, HW/perf resources, and finally
GEM's driver-release resources before GGTT/memory/MMIO release.

failure from entering the registration-only GEM release a second time.

## 2026-10-02 DRM failure-contract review and revised candidate 0008

The first 0008 rollback revision also introduced
`drm_atomic_helper_shutdown()` on the failed registration path. The frozen
Linux `i915_driver_probe()` failure branch proceeds to its GEM/display
unwind without that runtime-remove-only shutdown. The pinned NetBSD
`drm_atomic_helper_shutdown()` actively disables CRTCs. Since an unsuccessful
userspace registration need not imply a successful DRM publication or active
framebuffer, this extra hardware operation is not justified at this stage.
It was removed from the generator (commit `d86cfb76`), its source-order
regression (`0587d7ca`), and candidate 0008 (`e49aaac2`).

The frozen NetBSD DRM-core and i915 driver audit establishes the narrower
registration-failure contract for this exact target source:
- The i915 `drm_driver` enables MODESET but not DRIVER_LEGACY, and does
  not supply a `.load` callback.
- NetBSD's `drm_minor_register()` does not perform the fallible Linux
  debugfs/`device_add()` operations; `create_compat_control_link()` can
  return `-ENOMEM` if its temporary name allocation fails.
- On registration failure, `drm_dev_register()` already unregisters primary
  and render minors. The Linux reference still calls
  `drm_dev_unregister()` on its i915 error path; candidate 0008 preserves
  that sequence. The older NetBSD `drm_connector_unregister()` explicitly
  returns unless its connector is in REGISTERED state.
- The older NetBSD driver reports `VGT_DRV_DISPLAY_READY` before DRM
  registration; Linux's pinned driver also invokes `intel_vgpu_register()`
  before DRM registration. These are not proof of identical VM protocol
  behavior; no speculative change to vGPU signaling was made.

`tests/test_drm_registration_source_contract.py` was published in
commit `1c0175e9` to enforce these source assumptions with exact pinned
Linux/NetBSD Git revisions and to check the registration rollback structure.
Nine equivalent direct source assertions were executed against connector
and frozen DRM/i915 sources and passed. The repository Python regression
itself is **not yet run** against the checked-out pinned references.

After the atomic shutdown removal, a separate source-level reconstruction
of the generator's intended transformations matched the complete published
candidate 0008. All five 0008 unified-diff hunks matched exact unique source
contexts on frozen NetBSD and after 0007; candidate 0009 still matched its
single OpRegion hunk. This is an **in-memory, exact-context source check**,
not the pending Python-generator byte-comparison, native `git apply`,
NetBSD object/kernel compilation, or HP runtime validation. The remaining
DRM client/CRTC callback behavior on rare failed-registration paths is not
yet dynamically fault-injected.

## 2026-10-02 NetBSD-only RVDA map-failure unwind: candidate 0010

The frozen NetBSD OpRegion setup in `display/intel_opregion.c:1030-1051`
assigns the result of `AcpiOsMapMemory()` to `opregion->rvda`.
`intel_bios_is_valid_vbt()` rejects a NULL buffer
(`display/intel_bios.c:1933+`), but the invalid-RVDA branch then
unconditionally calls `AcpiOsUnmapMemory(opregion->rvda, rvds)`.
On the pinned NetBSD x86 path, `AcpiOsUnmapMemory()` delegates to
`acpi_md_OsUnmapMemory()` and then `_x86_memio_unmap()`; the latter
can panic on a virtual address that was never mapped. Linux's
`memunmap()` behavior must not be assumed for this NetBSD API.

`candidates/0010-netbsd-opregion-rvda-map-failure-unwind.patch`
(added `a14a1ccf`, normalized `7bf6c4b4`) guards only the NetBSD
`AcpiOsUnmapMemory()` call when RVDA is non-NULL. It leaves the
invalid-VBT fallback to the in-OpRegion VBT unchanged. Generator
`tools/generate_opregion_rvda_map_failure_patch.py`
(`92d9d8fd`) pins the NetBSD source and requires a unique branch
anchor. Test `tests/test_opregion_rvda_map_failure.py` (`75901372`,
wrapper correction `6899c85d`) extracts the real transformed C
branch for strict host C11/ASan/UBSan checks: absent ASLE,
zero ASLE RVDA, map failure/NULL, mapped-invalid VBT, and mapped-valid
VBT; it also demands generator byte equality and real
`git apply` composition with candidate 0009.

**Actual verification this step:** candidate 0010's single unified-diff
hunk matched the frozen source uniquely and generated exactly the
expected guarded branch in a source-only, in-memory application.
Candidate 0009 matched after 0010, and 0010 matched after 0009;
both orders produced identical combined OpRegion source. The
pinned BIOS NULL check and x86 unmap call chain were source-inspected.
**Additional isolated execution:** an independent local C11 harness using the pinned NetBSD RVDA branch with the 0010 guard passed all five intended cases with `-Wall -Wextra -Werror -pedantic -fsanitize=address,undefined`. A negative control, using the same harness with the original unguarded NetBSD unmap, terminated as expected on `assert(address != NULL)` (exit 134). The published Python test now enforces this same negative control (commit `fba485f9`), but that published test itself has **not executed** against the complete pinned NetBSD checkout.

**Still not run:** generator's Python byte-equality check, pinned-tree Python regression, actual `git apply` on the real clean/overlay worktrees, native NetBSD object/kernel build, and HP runtime verification. This is a reference-derived error fix
candidate, **not proof of the HP black-screen root cause**.

## 2026-10-02 Cherryview eDP fixed-mode failure: candidate 0011

The pinned Linux `drivers/gpu/drm/i915/display/intel_dp.c`,
`intel_edp_init_connector()`, rejects an eDP connector when its EDID/VBT
processing leaves no preferred fixed panel mode, calls its VDD-off
unwind, and does not proceed to the panel/backlight setup. The pinned
NetBSD `sys/external/bsd/drm2/dist/drm/i915/display/intel_dp.c`,
`intel_edp_init_connector()`, obtains an EDID-preferred mode or
`intel_panel_vbt_fixed_mode()` but **previously did not test whether
both failed**. It proceeded to the VLV/CHV reboot-notifier registration
and `intel_panel_init()/intel_panel_setup_backlight()` with a NULL
fixed mode. This is a concrete bounded source-semantics discrepancy,
not confirmed as the HP's historical F82 black-screen cause.

The NetBSD `intel_connector_alloc()` uses `kzalloc`, and its
`intel_connector_destroy()` normally frees a non-error cached EDID.
However, `intel_dp_init_connector()` on failed eDP initialization
calls `drm_connector_cleanup()` and then frees its allocation without
invoking the normal connector destroy callback. Candidate 0011
therefore (1) checks for a NULL fixed mode immediately after the
EDID/VBT fallback and mode-config unlock, **before** CHV notifier or
backlight initialization, and jumps to the existing VDD-off error
label, and (2) frees any cached non-error EDID, clearing its pointer
on that failure path. Existing DPCD-failure paths have NULL EDID from
the zeroed connector, so the new cleanup is conditional.

## 2026-10-02 eDP 1.4 AUX/DPCD supported-rates failure: candidate 0012

A new source-level discrepancy was found in the pinned NetBSD
`intel_dp.c:intel_edp_init_dpcd()` (NetBSD/src `03d918f6`,
around line 4434). It declares a stack
`__le16 sink_rates[DP_MAX_SUPPORTED_RATES]` and calls
`drm_dp_dpcd_read(..., DP_SUPPORTED_LINK_RATES, ...)` without checking
its return value. It then parses all entries until a zero terminator.
The frozen NetBSD `drm_dp_helper.c:drm_dp_dpcd_read()` documents a
transferred-byte count or a negative error; a failed/short AUX read
can therefore leave undefined or untrustworthy elements, which the
old i915 code interprets as advertised link rates and selects
`DP_LINK_RATE_SET` instead of its standard-rate fallback.

Pinned Linux `fd179f8a` handles the error path in
`intel_edp_set_sink_rates()`: unsuccessful supported-rate reading
clears the local array so no custom rates are accepted and default
DPCD link rates remain available. Candidate 0012 applies the same
failure behavior using the **older NetBSD AUX byte-count API**:
require `drm_dp_dpcd_read() == (ssize_t)sizeof(sink_rates)`, otherwise
log and zero the array before existing rate interpretation. Requiring
exact length also rejects short positive reads; the existing
`intel_dp_set_sink_rates()` and `intel_dp_set_common_rates()`
remain the hardware policy. This changes no MMIO registers or
firmware blobs and has not been proven the HP black-screen cause.

## 2026-10-02 Cherryview DPIO physical-route equivalence gate

The pinned Linux `drivers/gpu/drm/i915/display/intel_dpio_phy.c`
takes an explicit `vlv_dig_port_to_phy(dig_port)` for
`vlv_dpio_read(display, phy, ...)` in the CHV pre-PLL,
encoder and disable phases. Frozen NetBSD
`display/intel_dpio_phy.c` still uses
`vlv_dpio_read(dev_priv, pipe, ...)`.
The NetBSD `intel_sideband.c` call dispatches through
`dpio_phy_iosf_port[DPIO_PHY(pipe)]`, and frozen
`i915_reg.h` defines `DPIO_PHY(pipe)=pipe >> 1`.
NetBSD `intel_init_dpio()` maps `DPIO_PHY0` to
`IOSF_PORT_DPIO_2` and `DPIO_PHY1` to
`IOSF_PORT_DPIO`.

Crucially, the older NetBSD `intel_dp.c` **and**
`intel_hdmi.c` Cherryview encoder masks allow ports B/C
only on pipes A/B and port D only on pipe C. The actual
NetBSD `vlv_dport_to_phy()` maps ports B/C to PHY0
and D to PHY1. Thus for **all five permitted B/C/D
port-pipe combinations**, the old `DPIO_PHY(pipe)`
and newer explicit `PHY(port)` resolve to the **same**
physical IOSF destination. Invalid combinations such
as port B/pipe C or port D/pipe A would break this
equivalence; any future pipe-mask expansion must
therefore change the DPIO API/callers together.

The reference-pinned `tests/test_chv_dpio_routing_source_contract.py`
(commit `a7a681382587576c271cb166371e1fba7d8f4193`)
records the actual NetBSD/Linux file-level mappings
and the five valid pairs; its source inputs were added

and its invocation in the common runner
in `9b330ece493aada0832fdc7e1a264dafd174fdef`.
